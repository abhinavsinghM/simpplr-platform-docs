The Extensibility Center is the developer surface of the Simpplr platform. It exposes the same intranet primitives your users work with in the product — sites, content, feeds, files, people, tasks, search — as REST APIs you can build against.

Use it to centralize workplace applications inside Simpplr, push and pull data between Simpplr and your other systems, and automate work that would otherwise be manual.

## Two APIs, one platform

| | [User API](/authentication/user-tokens) | [B2B API](/authentication/b2b-tokens) |
|---|---|---|
| Acts as | A specific signed-in person | Your application, tenant-wide |
| OAuth grant | `authorization_code` (+ `refresh_token`) | `client_credentials` |
| Sees | Only what that person is entitled to see | Tenant-wide, subject to the actor you name |
| Typical use | An app or extension acting for a logged-in user | Backend sync, provisioning, scheduled jobs |
| Operations | 67 across 14 areas | 75 across 13 areas |

Both are documented endpoint-by-endpoint in the **User API** and **B2B API** tabs above. See [Choosing an API](/get-started/choosing-an-api) for the full capability comparison — several areas exist in only one of the two.

## Conventions that apply everywhere

Before you write much code, four things are worth knowing up front:

- Every response is wrapped in a **`status` / `message` / `result` envelope** rather than returning the object directly — see [Platform Conventions](/concepts/conventions).
- **Pagination is token-based**, but the parameter names vary by endpoint family — see [Pagination](/concepts/pagination).
- **Error bodies come in several shapes** across endpoint families, so parse defensively — see [Errors](/concepts/errors).
- On the **B2B API, most writes require you to name the acting user** (`createdBy`, `modifiedBy`, `deletedBy`). There is no signed-in user to infer it from — see [Acting on Behalf of Users](/concepts/acting-as-users).
